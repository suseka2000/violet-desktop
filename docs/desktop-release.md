# Настольные приложения Violet

Оболочка Electron запускает локальный Python-сервис, упакованный PyInstaller
в `onedir`. Пользователю не нужны Python, Node, браузер или установленный CAD.
Проекты и вычисления остаются на компьютере. У каждого приложения собственный
каталог данных вне установленной программы; обновление не заменяет эту папку.

## Что входит в сборку

`desktop/build/bundle_policy.py` задаёт явный список исходников интерфейса,
серверных модулей, шрифтов и четырёх файлов правил. Отдельный проверенный список
`desktop/build/approved-step-library.json` содержит 80 STEP-файлов и 8 материалов
из папки методичек поставщика, передачу которых приглашённым пользователям
владелец разрешил 20 октября 2026 года. SHA-256 проверяется перед каждой
сборкой. Добавление нового файла в папку моделей само по себе не добавляет его
в установщик: список нужно обновить и проверить.

Не включаются `data/`, `output/`, `tmp/`, исходные DWG/DXF, PDF «Оружейная палата»,
SolidWorks/КОМПАС, личные проекты, журнал работы, экспортированные
альбомы и секреты. Методички из отдельного разрешённого списка входят в закрытую
поставку и подтверждают выписанные правила по SHA-256; отсутствующие или
изменённые первоисточники не объявляются проверенными.
LibreDWG и ODA File Converter не поставляются. DXF и STEP
обрабатываются встроенными компонентами; прямое чтение DWG требует отдельно
настроенного допустимого конвертера.

Нативные бинарные зависимости собираются на той же ОС и архитектуре, что и
итоговое приложение: Windows x64, macOS Apple Silicon, macOS Intel.
Нельзя положить macOS-версию Open CASCADE в установщик Windows.

## Локальная проверочная сборка

Из корня проекта, в Python 3.12:

```sh
python -m pip install -r requirements-desktop-build.txt
python -m unittest tests.test_desktop_packaging
python desktop/scripts/build_backend.py
python desktop/scripts/prepare_release.py
```

Затем из `desktop/`:

```sh
pnpm install --frozen-lockfile
pnpm test
pnpm run pack:preview
```

Для архивов и установщиков вместо `--dir` указать `--mac --arm64`, `--mac --x64`
или `--win --x64` на соответствующей системе. macOS создаёт DMG для установки и
ZIP, обязательный для механизма обновления; Windows — NSIS EXE.

Проверочная сборка не включает обновления и не притворяется подписанной.
macOS может отклонять неподписанное приложение на другом компьютере.
Для нормальной передачи людям требуется производственный выпуск ниже.
`desktop/stage/bundle-inputs.json` — локальная ведомость входов; в установщик
попадает `bundle-inventory.json` без абсолютных путей компьютера разработчика.
Ключ `--without-library` предназначен только для диагностики пустой библиотеки.

## Производственный выпуск

Нужны постоянный идентификатор приложения `com.violet.interior-rd`, сертификаты
издателя, приватный GitHub-репозиторий релизов и завершённый комплект лицензий зависимостей.
Проверка намеренно запрещает выпуск, если эти условия не выполнены.

Для macOS нужны Apple Developer ID Application, подпись вложенных Python/CAD
библиотек и notarization. Для Windows — Authenticode-сертификат; его издатель
должен совпадать с `VIOLET_WINDOWS_PUBLISHER_NAME`. Самоподписанный сертификат не
является заменой доверенной подписи для внешней установки.

Настройки передаются только через переменные окружения/секреты сборочного
окружения:

| Настройка | Назначение |
| --- | --- |
| `VIOLET_RELEASE=1` | Включает обязательную подпись и производство |
| `VIOLET_GITHUB_OWNER` | Владелец приватного репозитория релизов |
| `VIOLET_GITHUB_REPOSITORY` | Имя приватного репозитория релизов |
| `CSC_LINK`, `CSC_KEY_PASSWORD` | Сертификат и пароль; отдельно для каждой ОС |
| `CSC_NAME` | Альтернатива: подходящий сертификат в хранилище сборочной машины |
| `VIOLET_WINDOWS_PUBLISHER_NAME` | Точное имя издателя сертификата Windows |
| `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID` | Учётные данные notarization |
| `APPLE_API_KEY`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER` | Альтернатива notarization через API |

После подготовки зависимостей и нативного backend:

```sh
python desktop/scripts/collect_notices.py --require-release-ready
python desktop/scripts/prepare_release.py --release
```

Далее `pnpm run dist:release --mac --arm64` (или соответствующие ОС/архитектура).
Обёртка обязательно выставляет производственный режим и повторяет проверку;
случайно получить неподписанную проверочную версию этой командой нельзя.
Она запускает нативную команду electron-builder с `--publish never`: не публикует
приложение, но готовит файлы метаданных обновления. Не менять вручную их SHA-512.
Лицензии Python/PDFium и Noto Sans собираются автоматически. Лицензии OCP/OCCT
включены отдельно, поскольку их wheel не содержит полный набор текстов.
`desktop/build/native-license-review.json` пока честно фиксирует оставшуюся
проверку транзитивных нативных библиотек. Нельзя просто поменять флаг
`redistribution_reviewed`: сначала приложить недостающие тексты и результаты
проверки конкретного wheel каждой платформы.

## Обновления без ручной переустановки

Версия приложения повышается в `desktop/package.json` перед выпуском. Клиент
проверяет обновление, скачивает его, проверяет контрольную сумму и подпись
издателя, затем устанавливает при согласованном перезапуске. Пользователь не
скачивает и не запускает установщик вручную. При этом обновление действительно
может заменять пакет программы целиком; дифференциальная загрузка зависит от
платформы, доступных blockmap и ответа хранилища. Это не обещание «скачивать
только несколько изменённых строк».

Данные отделены от программы. Перед применением обновления не должно быть
активной сборки, несохранённых правок или записи базы. На сервере обновлений
нужно сохранять предыдущий установщик для восстановления и выполнять
проверку миграции на копии базы.

Сначала создаётся черновик выпуска в приватном репозитории. В него загружаются
подписанные EXE/ZIP/DMG и blockmap всех трёх платформ, проверяются размер и
контрольные суммы, затем добавляются `latest.yml` / `latest-mac.yml`. Обе
архитектуры macOS должны быть перечислены в одном `latest-mac.yml`; нельзя
перезаписать файл ARM-выпуска метаданными Intel. После проверки черновик
переводится в опубликованный приватный выпуск. Не удалять старые артефакты,
пока установленный клиент или метаданные могут на них ссылаться.

После скачивания трёх CI-артефактов можно собрать проверенный локальный набор:

```sh
node scripts/combine-release.cjs NEW_RELEASE_DIR MAC_ARM_DIR MAC_INTEL_DIR WINDOWS_DIR
```

Команда запускается из `desktop/`, не обращается к сети, проверяет SHA-512
каждого файла из метаданных, объединяет два macOS-манифеста и создаёт новый
каталог без перезаписи старого. Проверка подписей и публикация остаются
отдельными обязательными шагами; контрольная сумма не заменяет подпись.

Доступ только приглашённым: использовать приватный репозиторий GitHub Releases
или собственный HTTPS-шлюз с индивидуальной аутентификацией. Публичные Releases
и открытое хранилище для этого проекта не подходят. Обычная страница GitHub
Releases — не generic URL каталога обновлений.

Приватный GitHub provider в electron-updater 6.8.9 поддерживает персональный
токен пользователя с правом чтения выбранного репозитория. Пользователя сначала
приглашают в репозиторий; учётные данные хранятся только на его компьютере через
защищённое хранилище ОС. Нельзя встраивать общий PAT разработчика, писать его в
app-update.yml, логи или переменные среды готового установщика. Владелец может
отозвать дальнейший доступ к обновлениям, но не уже скачанную офлайн-копию
программы. Для более простого входа без ручных токенов нужен отдельно
настроенный OAuth/GitHub App или сервер приглашений.

Обновления подписываются тем же издателем. Не отключать проверку подписи и
не соглашаться на TLS-ошибки ради «работающего» обновления. Переход на нового
издателя требует отдельного проверенного плана.

## Нативная сборка в CI

Перед первой передачей исходников в приватный репозиторий создайте отдельную
чистую копию из корня проекта:

```sh
python desktop/scripts/stage_sources.py /absolute/new-source-copy
```

Скрипт использует только проверенный `desktop/build/source-files.json` и
отдельный список разрешённой библиотеки, отказывается от существующего
каталога назначения, проверяет ссылки и распространённые форматы секретов.
Он не запускает Git и ничего не загружает. Файл `source-stage-manifest.json`
позволяет проверить состав копии до любой внешней отправки. После добавления
нового исходника его нужно явно внести в список; текущую рабочую папку целиком
в репозиторий отправлять не нужно.

`.github/workflows/desktop-build.yml` запускается вручную и собирает три
независимых артефакта только в приватном репозитории.
Ничего не публикует в Releases или на внешний сервер.
Настройте защищённое окружение `desktop-release` с ручным одобрением и
секретами каждой ОС; без секретов доступны только проверочные сборки.
Репозиторий исходников, запуск CI и публикация должны быть явно согласованы
владельцем. Библиотека STEP попадает в CI только вместе с разрешёнными файлами;
если в checkout их нет, сборка останавливается, а не делает неполный пакет.

Минимальная приёмка каждого выпуска: чистая установка на другой машине;
создание/сохранение проекта; PDF/DXF; STEP и 3D; закрытие приложения без
процессов-сирот; обновление с предыдущей подписанной версии с сохранением
проекта; отказ от подменённой/неподписанной загрузки.
