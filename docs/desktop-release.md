# Приложения Violet для Windows и macOS

Electron запускает встроенный Python/CAD-сервис. Пользователям не нужны Python,
Node или браузер. Данные и вычисления остаются на компьютере; папка проектов
отделена от установленного приложения и не заменяется обновлением.

## Приватная поставка без платных сертификатов

Основной вариант — закрытый репозиторий `suseka2000/violet-desktop` и бесплатная
подпись обновлений Ed25519. Приложение содержит только публичный ключ. Перед
установкой проверяются подпись манифеста, версия, платформа, архитектура,
точное имя, размер и SHA-256 установщика. Неподписанный или изменённый файл,
понижение версии и подмена платформы отклоняются.

Это собственная подпись обновления, а не сертификат Apple/Microsoft. При первой
установке ОС может показать предупреждение о неизвестном разработчике или
заблокировать запуск. Программа не отключает Gatekeeper, SmartScreen, проверку
TLS или другие средства защиты. Возможность разрешить запуск зависит от
настроек и политики конкретного компьютера. Платные сертификаты остаются
необязательным отдельным режимом, но не требуются для сборки приватного выпуска.

Закрытый GitHub отвечает за доступ, Ed25519 — за подлинность обновления.
Приглашённый пользователь вводит свой токен с правом чтения только нужного
репозитория; он хранится в защищённом хранилище ОС. Общего токена разработчика
в установщике нет. Отзыв приглашения прекращает доступ к новым обновлениям,
но не удаляет ранее скачанную офлайн-копию приложения.

## Состав установщика

Явный список исходников, интерфейса, шрифтов и правил задаёт
`desktop/build/bundle_policy.py`. Разрешённый владельцем список
`desktop/build/approved-step-library.json` содержит 80 STEP и 8 методичек
поставщика; каждый файл проверяется по SHA-256.

В пакет не входят пользовательские базы, проекты, экспортированные альбомы,
исходные DWG/DXF, PDF «Оружейная палата», файлы SolidWorks/КОМПАС, секреты и
временные файлы. ODA/LibreDWG не включены. Для прямого импорта DWG нужен отдельный
допустимый конвертер; DXF и STEP поддерживаются встроенными компонентами.

Windows x64, macOS ARM64 и macOS Intel собираются каждый на своей нативной
системе. Python backend запускается как `onedir`, а не распаковывает сотни
мегабайт заново при каждом запуске.

## Сборка

Из корня проекта, Python 3.12:

```sh
python -m pip install -r requirements-desktop-build.txt
python -m unittest tests.test_desktop_packaging tests.test_desktop_runtime tests.test_desktop_library_io tests.test_desktop_source_staging
python desktop/scripts/build_backend.py
```

Из `desktop/`, Node 22.12+ и pnpm 11.25.0:

```sh
pnpm install --frozen-lockfile
pnpm test
pnpm run dist:release --mac --arm64
```

На Intel Mac использовать `--mac --x64`, на Windows — `--win --x64`.
`dist:release` создаёт приложение с приватными обновлениями, но не публикует
файлы и не имеет доступа к приватному ключу. Для локальной диагностики есть
`pack:preview` (только `.app`/каталог) и `dist:preview` (обновления отключены).
DMG предназначен для первой установки на Mac; обновление использует ZIP.
Windows создаёт установщик NSIS для текущего пользователя, без повышения прав.

Обычной приватной сборке не нужны дополнительные переменные: репозиторий и
публичный ключ уже заданы. Для другого закрытого репозитория доступны
`VIOLET_GITHUB_OWNER` и `VIOLET_GITHUB_REPOSITORY`. Публичный ключ по умолчанию
читается из `desktop/build/update-public-key.json`. Нельзя менять его случайно:
уже установленные клиенты доверяют прежнему ключу.

## Подготовка обновления

Поднять версию `desktop/package.json`, собрать все платформы, проверить их,
скачать результаты CI. Приватный ключ хранится отдельно от репозитория:

`/Users/z123/Documents/Codex/violet-release-keys/release-private.pem`

Не отправлять его в GitHub, Actions, установщик, чат или журнал. Сделать
защищённую резервную копию: потеря ключа нарушит возможность обновлять
установленные приложения. Для нового независимого продукта пару создают
однократно командой `node scripts/sign-release.cjs keygen OUTSIDE_REPO_DIRECTORY`;
существующая папка и ключи никогда не перезаписываются.

Из `desktop/`, для каждого готового артефакта:

```sh
node scripts/sign-release.cjs sign \
  --artifact /absolute/Violet-0.4.0-mac-arm64.zip \
  --platform darwin --arch arm64 --version 0.4.0 \
  --key /Users/z123/Documents/Codex/violet-release-keys/release-private.pem \
  --output /absolute/release-manifests
```

Для Intel — `darwin`/`x64`; для Windows — `win32`/`x64` и
`Violet-0.4.0-win-x64.exe`. Скрипт проверяет соответствие приватного ключа
публичному ключу приложения, читает файл потоково, подписывает точные байты
JSON и проверяет собственную подпись. Ничего не загружает, старые манифесты
не перезаписывает. Манифест содержит ровно:

```json
{"schema":"violet-update/1","version":"0.4.0","platform":"darwin","arch":"arm64","filename":"Violet-0.4.0-mac-arm64.zip","size":123,"sha256":"..."}
```

В приватном GitHub создать черновик релиза с тегом `v0.4.0`. Сначала загрузить
все проверенные установщики ZIP/EXE и установочные DMG, затем соответствующие
`violet-update-darwin-arm64.json`, `violet-update-darwin-x64.json`,
`violet-update-win32-x64.json` и их `.json.sig`. Опубликовать закрытый релиз
только после проверки полного набора. Старые артефакты сохранять для
восстановления. `latest.yml` больше не является каналом доверия этого клиента.

Обновление загружает готовый пакет программы; это не обещание дифференциальной
загрузки. Перед заменой приложение проверяет отсутствие несохранённых правок,
активных расчётов и записи базы. На следующем запуске перед миграциями создаётся
согласованная резервная копия базы. Пользовательские STEP и проекты сохраняются.

## CI и безопасная передача исходников

```sh
python desktop/scripts/stage_sources.py /absolute/new-source-copy
```

Команда создаёт отдельную чистую копию из точного списка
`desktop/build/source-files.json` и разрешённых 88 файлов библиотеки. Она
отвергает ссылки/секреты, не перезаписывает существующую папку, создаёт
запрещающий всё нерассмотренное `.gitignore`, не вызывает Git и ничего не
отправляет. Публичный ключ JSON включён; приватные PEM — нет.

`.github/workflows/desktop-build.yml` запускается вручную только в приватном
репозитории. `release=true`, `certified=false` — обычные бесплатные приватные
приложения. Три нативных задания проходят тесты, замораживают backend,
проверяют настоящие STEP/PDF/DXF и сохранность данных, затем дают артефакты.
CI не публикует Releases и не содержит ключ Ed25519. Ограничение времени задания
— 30 минут; финансовый лимит GitHub настраивается отдельно владельцем аккаунта.

Режим `certified=true` необязателен и требует `release=true`, настроенных
`CSC_LINK`/`CSC_KEY_PASSWORD` или `CSC_NAME`, издателя Windows и, для Mac,
учётных данных notarization. Секреты сертификатов передаются только шагам
проверки и упаковки, не установке зависимостей. Пустые сертификаты не меняют
обычный бесплатный путь.

## Лицензии и приёмка

`collect_notices.py` собирает тексты лицензий 18 Python-пакетов, PDFium,
шрифтов, OCP и OCCT; также формирует перечень нативных файлов с SHA-256,
размером, компонентом и ссылками на исходники. Реальные недостающие сведения
перечислены отдельно в `native_components_missing_matching_license_texts`
и `desktop/build/native-license-review.json`. Название DLL/номер ABI не
выдаётся за доказательство версии исходников.

Незавершённая проверка лицензий видна в отчёте и не мешает локально собрать
приложение для проверки. До передачи получателям нужно дополнить соответствующие
уведомления и выполнить применимые обязательства по исходникам. Подпись
Ed25519 подтверждает автора выпуска, а не юридическую готовность зависимостей.
`python desktop/scripts/collect_notices.py --require-release-ready` остаётся
отдельной проверкой готовности комплекта уведомлений.

Минимальная приёмка: чистая установка на обеих ОС; проект/PDF/DXF/STEP/3D;
закрытие без процессов-сирот; обновление с предыдущей версии с сохранением
данных; отказ при изменённом ZIP/EXE, манифесте или подписи; отказ в обновлении
во время расчёта/несохранённой правки; восстановление после неудачной замены.
